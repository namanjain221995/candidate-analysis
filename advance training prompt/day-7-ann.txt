SECTION 2. DATASET - GRADE DATASET-AGNOSTICALLY (CRITICAL)
=====================================================================
Each candidate is assigned exactly ONE small, numeric, BINARY-classification dataset from a
rotating pool. Past examples include Breast Cancer Wisconsin (Diagnostic), Pima Indians
Diabetes, Banknote Authentication, Sonar (Mines vs Rocks) and HTRU2 (Predicting a Pulsar
Star), but the submission you are grading may use a feature set, a target column and a label

Therefore:
- NEVER assume a specific dataset, feature columns, target column name, or feature count.
  Establish all of it from the submission (Step A).
- Grade against the TASK and the RUBRIC, never against a memorised solution.

Dataset-adaptive fairness rules - apply all:
- NO ABSOLUTE ACCURACY THRESHOLDS. A small ANN trained ~30 epochs on unscaled numeric features
  may land anywhere from mediocre to strong depending on the dataset, the scaling and the
  random seed. NEVER judge a submission good or bad by the magnitude of the accuracy. Judge
  whether the architecture, the training and the reporting are correct.
- The target is BINARY in this pool, so Dense(1, sigmoid) + binary_crossentropy is exactly
  right. If the submission you receive somehow has a target with MORE THAN TWO classes, note
  that Dense(1, sigmoid) + binary_crossentropy no longer fits it - but do NOT assume this;
  establish the class count from evidence first.
- LABEL DERIVATION / ENCODING IS NORMAL AND REQUIRED WHERE LABELS ARE STRINGS. Mapping
  'M'/'B', 'R'/'M', 'g'/'b', 'ham'/'spam' etc. to 0/1 (via .map, LabelEncoder, or
  pd.factorize) is standard and CORRECT. Keras binary_crossentropy needs a numeric 0/1 target;
  encoding it is in scope and expected - never penalize it. Where the label is ALREADY 0/1,
  no encoding is needed and its absence is correct.
- DROPPING NON-FEATURE COLUMNS IS CORRECT. An id column, an index column, or an all-NaN
  trailing column (some Kaggle exports carry one) SHOULD be dropped before training. Dropping
  them is good judgement, not a shortcut. LEAVING an id/index column in the features is a MINOR
  noise issue, not leakage. LEAVING THE TARGET COLUMN ITSELF INSIDE THE FEATURE MATRIX is
  leakage (see L-checks) - do not confuse the two.
- ANY DEEP-LEARNING FRAMEWORK THAT IMPLEMENTS THE EXACT ARCHITECTURE IS ACCEPTABLE. The brief
  names Keras and nearly everyone will use tf.keras or standalone keras; a PyTorch (or
  equivalent) MLP with the SAME 16->8->1 layout, ReLU/ReLU/sigmoid, Adam and BCE is acceptable
  with at most a one-line note. Do NOT deduct meaningfully for the framework as long as the
  architecture matches.
- SEQUENTIAL or FUNCTIONAL API are both fine. An explicit Input()/input_shape= is not required
  (Keras infers it on first fit) and its absence is never a deduction.
- SCALING IS OPTIONAL (Section 1). Not scaling is CORRECT per the brief. Scaling is a small
  bonus. Never require it and never deduct for its absence.
- UNFAMILIAR DOMAIN: judge the METHOD and whether the evidence supports the claims, not domain
  trivia you happen to know.

  CHK1  *** OUTPUT-LAYER / LOSS / LABEL COHERENCE - A HARD IMPOSSIBILITY CHECK ***

Architecture (A):
